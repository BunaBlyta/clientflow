# Mobile: stopped notes scroll fighting the keyboard animation

- Follow-up to the earlier keyboard-gap fix: user reported the composer still "doesn't really go up smoothly" once the gap itself was gone.
- Root cause: `app/(app)/projects/[id]/notes.tsx`'s chat `ScrollView` had `onContentSizeChange={() => scrollRef.current?.scrollToEnd({ animated: false })}`. This fires on any content-size change, not just "a new message arrived" — and `KeyboardAvoidingView`'s padding growing as the keyboard animates open shrinks the `ScrollView`'s available height, which (under `contentContainerStyle={{ flexGrow: 1 }}`) changes its measured content size too. So an unanimated `scrollToEnd` was firing repeatedly during the keyboard's own smooth slide animation, snapping the scroll position on every frame and reading as jerky motion layered on top of what should have been one continuous animation.
- Fix: moved the scroll-to-newest-message behavior out of `onContentSizeChange` and into a `useEffect` keyed on `notes.length`, wrapped in `requestAnimationFrame` (matching the existing pattern already used in `handleSend` for the same reason — letting layout settle before measuring). This only fires when a message is actually added (initial load or new note), not on keyboard-driven resize churn.
- Verified with `npx tsc --noEmit` from `mobile/`. Not tested on a device this session.

No content was lost — both entries are intact — but it's worth the user knowing two agents are both writing mobile lane state right now, since the working agreement assumes one writer per lane file.
