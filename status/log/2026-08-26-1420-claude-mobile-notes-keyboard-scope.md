# Mobile: scoped keyboard-avoiding padding to just the notes composer

- Second follow-up on the notes keyboard animation: after the earlier scroll-jank fix (moving auto-scroll off `onContentSizeChange`), user reported the composer "still doesn't open smoothly with the keyboard."
- Cause: `app/(app)/projects/[id]/notes.tsx` wrapped the *entire* screen return — `AtmosphereBackground`, the sticky header, the full chat `ScrollView`, and the composer — in one `KeyboardAvoidingView` with `behavior="padding"` (iOS). Because the `ScrollView` and composer are siblings in that same flex column, every frame of the keyboard's open/close animation forced Yoga to recompute the `ScrollView`'s flex-grow sizing (a potentially long chat history) in lockstep with the composer's own animating padding — expensive per-frame work that reads as jank, independent of the scroll-jank issue already fixed.
- Considered `ScrollView`'s `automaticallyAdjustKeyboardInsets` (native, RN 0.86 confirmed to have it) as an alternative — decided against combining it with the composer's own padding-behavior `KeyboardAvoidingView` in the same pass, since both would be independently compensating for the keyboard and could double up (the same class of bug as the original hardcoded-offset issue). Kept the fix to one mechanism.
- Fix: restructured so only the composer `View` is wrapped in its own `KeyboardAvoidingView` (`behavior={Platform.OS === 'ios' ? 'padding' : undefined}`), sitting as a sibling after the `ScrollView` inside a plain (non-keyboard-avoiding) outer `View`. The header and message list are no longer inside any keyboard-avoiding container.
- Verified with `npx tsc --noEmit` from `mobile/`. **Not verified on a device this session** — this is a structural/performance change reasoned from how `KeyboardAvoidingView` and Yoga flex layout interact, not confirmed visually. Told the user to confirm before treating this as closed.
- Committed `mobile/app/(app)/projects/[id]/notes.tsx` alone.
