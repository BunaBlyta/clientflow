## 2. Four defects found on 12 Aug — all [verified], all in Flow A

Flow A is the demo: prospect requests a package → staff approves → client onboards
by email code → pays the deposit → the project advances. It is the most important
path in the project and it has breaks in it.

### 2.1 Approving a request creates no project and no invoice

**[verified]** — read `app/api/requests/[id]/route.ts` in full. It creates the
`User`, creates the `Client`, sets the request to `APPROVED`, sends the email, and
stops. Re-check:

```
grep -n "project\.create\|invoice\.create" 'app/api/requests/[id]/route.ts'   # expect: nothing
```

Consequence: a client who onboards through approval logs in to an empty app. No
project, no deposit invoice, nothing to pay.

**Why this hid for so long:** the Stripe payment proven on 11 August was against
seeded `inv-5`, which belongs to a seeded client — not to anyone who came through
approval. Both halves of the chain are genuinely unmocked, which is exactly what
disguised the missing join. **If an agent reports a chain "verified end to end",
check the seam, not the ends.**

### 2.2 The verification code is consumed twice, stranding the client

**[verified]** — read both route files. `POST /api/auth/verification/verify` and
`POST /api/auth/set-password` each validate the code against
`verificationCodeHash`, and **each nulls it on success**. Re-check:

```
grep -n "verificationCodeHash: null" \
  app/api/auth/verification/verify/route.ts app/api/auth/set-password/route.ts
```

So the intended two-screen mobile flow — enter code, then choose password — fails
at step two with "Invalid or expired verification code", leaving the account
active with **no password**.

**[verified]** Not an auth hole: `verifyPassword` in `app/api/_lib/auth.ts:91-92`
returns false on a null hash, so login correctly rejects them. They are simply
stuck.

**Fix decided:** make `/verification/verify` a pure check that writes nothing;
leave `set-password` as the single consumer of the code.

### 2.3 `PENDING` + `DEPOSIT` are load-bearing, and failing them is silent

**[verified]** — `app/api/stripe/webhook/route.ts:73`:

```ts
if (invoice.type === 'DEPOSIT' && project?.status === 'PENDING') {
  // → project moves to DISCOVERY, and a system note is written to the feed
}
```

If the project is created in any other status, or the invoice as any other type,
the webhook still returns 200, the invoice still moves to `PAID`, and **the project
silently never advances and no system note is written.** Nothing errors, nothing
logs. The payment gate — the single most important behaviour in the project —
would just quietly not exist.

**[verified]** `ProjectStatus` is `PENDING DISCOVERY DESIGN DEVELOPMENT REVIEW
LAUNCHED CANCELLED ON_HOLD` — there is **no `APPROVED`**. `AGENTS.md` §4 describes
the transition as "Approved → Discovery", which is wrong about the name.

**[verified]** There is no `prisma/project-state.ts`. Only `prisma/invoice-state.ts`
(plus its test). Do not let an agent invent a project state machine.

### About touching Buna's machine

These are process rules earned the hard way in this session:

- **Never pass `force: true` to `device_commit_files`.** The mtime guard exists to
  stop you clobbering Buna's edits. If it fires, re-stage and diff. A sub-second
  mtime mismatch is not a licence to disable it across a batch.
- **Never tell Buna to `rm .git/index.lock` unconditionally**, and never while
  agents are running in the shared checkout — a lock held by an agent mid-commit is
  real, and removing it risks a corrupted index or a lost commit. Check
  `pgrep -fl "git "` and the lock's age first.
- **Use `git --no-optional-locks status` for reads from the sandbox.** Plain
  `git status` takes the index lock and the sandbox cannot release it, which is what
  creates the stale lock in the first place.
- **Do not run git write commands from the sandbox at all** — hand Buna the command.
  `git push` has no credentials, and writes leave lock files the sandbox cannot
  unlink.
- **Do not write `STATUS.md`** — Buna owns it. Agents write only their own
  `status/CURRENT-*.md` plus a **new** file in `status/log/`.

### About the deploy — these are [unverified] predictions, not findings

Reasoning about this stack, not checked against the repo's Vercel config. Verify
each before relying on it:

- `package.json`'s build script is **[verified]** `next build` with no
  `prisma generate`. **[unverified]** that this breaks on Vercel — but it is the
  most common first-deploy failure on this stack. Consider
  `"build": "prisma generate && next build"`.
- **[unverified]** Neon needs the pooled connection string for serverless.
- **[verified]** `app/api/stripe/checkout/route.ts:68` uses
  `process.env.APP_URL ?? request.nextUrl.origin`, so `APP_URL` should be set
  explicitly.
- **[verified]** `middleware.ts` gates CORS to `NODE_ENV === "development"` and
  localhost origins, and its matcher includes `/api/:path*`. So a deployed API will
  reject `expo start --web` from any non-localhost origin. **Demo mobile against the
  local API.**
- **[unverified, from `docs/HANDOVER-2026-08-11.md`]** `SESSION_SECRET` throws in
  production if unset, and `stripe listen` issues a new `whsec_` each run — a
  deployed webhook needs its own secret from the Stripe dashboard.
- **[verified]** Local and Vercel would share one Neon database. `npx prisma db seed`
  is rerunnable and resets invoice statuses — do not reseed near a demo.
