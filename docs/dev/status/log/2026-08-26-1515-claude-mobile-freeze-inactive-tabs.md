# Mobile: froze inactive tabs to fix the theme toggle's real re-render cost

- Continuation of the theme toggle saga. The rAF-buffering fix (giving the heavy re-render two frames before starting the fade-back-in) did not help — user tested on-device and confirmed the lag persisted "in the dead middle," which meant the underlying work is longer than a couple of frames, not a scheduling race.
- Asked the user how to proceed given the remaining fix (reducing what re-renders on a theme change) touches tab-mounting behavior app-wide, not just the toggle. User chose to test on their phone first; after confirming the problem was still there, gave the go-ahead implicitly by reporting back rather than picking "leave it as-is."
- This time, instead of guessing from general React Navigation knowledge (which does not directly apply — this Expo Router version bundles its own navigation internals; there is no standalone `@react-navigation/bottom-tabs` package in `node_modules`), read the actual installed source before making any change, per this project's "Expo HAS CHANGED, read the exact versioned docs" instruction:
  - `node_modules/expo-router/build/react-navigation/bottom-tabs/views/BottomTabView.js`: confirms the JS `Tabs` component passes `freezeOnBlur` and `enabled={detachInactiveScreens}` through to react-native-screens' `Screen`/`MaybeScreen`, with `shouldFreeze: activityState === STATE_INACTIVE && !isPreloaded`.
  - `node_modules/react-native-screens/src/components/Screen.tsx`: confirms `freezeOnBlur` (defaulting to a global `freezeEnabled()` flag) only has any effect inside the `if (enabled && isNativePlatformSupported)` branch — when `enabled` (i.e. `detachInactiveScreens`) is `false`, the component takes a different code path (a plain `Animated.View` toggling `display: none`) that does not wrap children in `DelayedFreeze`/`<Freeze>` at all.
  - `node_modules/react-native-screens/src/components/helpers/DelayedFreeze.tsx`: confirms the actual mechanism is `react-freeze`'s `<Freeze>` component, which pauses React re-rendering of its subtree while frozen, without unmounting (state, scroll position, in-flight/cached data all preserved) — exactly the semantics needed. Verified `react-freeze` is actually present in `node_modules` (a transitive dependency of `react-native-screens`), so this isn't going to fail at runtime from a missing module.
- Fix: `app/(app)/_layout.tsx` — changed `detachInactiveScreens={false}` to `detachInactiveScreens` (true), and added `freezeOnBlur: true` to the `Tabs`' `screenOptions`. `lazy: false` is untouched, so all 5 tabs still mount immediately on app load as before; the only change is that once a tab isn't focused, its React subtree stops re-rendering (frozen) rather than continuing to fully re-render on every context change (like a theme switch) while backgrounded.
- This directly targets the actual root cause identified across the last several rounds: a theme toggle was re-rendering all 5 mounted tab screens simultaneously, regardless of which one was visible. With this change, a theme toggle should only re-render the currently focused tab.
- Verified with `npx tsc --noEmit` from `mobile/` (confirms `freezeOnBlur` is a recognized, typed screen option in this version). Not verified on a device this session — recommended the user check it, since this is the first fix in this saga grounded in reading the actual library implementation rather than reasoning about behavior in the abstract.
- Committed `mobile/app/(app)/_layout.tsx` alone (it also carried some unrelated pending styling tweaks — tab label font weight, tab icon stroke width — already uncommitted in that file before this change; consistent with the user's earlier go-ahead to bundle such pending work in rather than hold up a fix waiting to isolate it).
