# Mobile: theme toggle — dim real content instead of animating color

Continuation of a long session-long back-and-forth on the account tab's theme toggle. Sequence of approaches tried, each rejected for a different reason, all without device verification:

1. Overlay flash (existing, at session start) — masking an instant swap behind a translucent rectangle. Tuned peak opacity and timing several times: too transparent read as a snap, too opaque read as a solid black/white flash, blended-color version and native-driven-opacity version both still read as a "pulse."
2. Real per-element crossfade via `useAnimatedThemeColor` (a `progress` Animated.Value interpolating actual colors), applied to ~19 elements on the account screen — reported "harsh" (the non-animated `mode` snap fired at t=0, clashing with animated elements for the whole transition).
3. Deferred the `mode` snap to the animation's completion instead of its start — user said no visible difference, then specified "fades, but choppy/stuttery" when asked for detail, pointing at real per-frame performance cost from ~19 concurrent JS-driven (color can't use native driver) interpolations.
4. Cut scope to 5 elements (background + 2 main cards) — "better, but... changes colors... before settling... increases contrast" — the 2 cards' backgrounds/borders finished animating before their own static text snapped, reading as a contrast pop timed to the settle moment.
5. Cut further to 1 element (background only) — "the bg color darkens before the cards text buttons and other elements" — with nothing else animating, the background necessarily led everything else for the whole duration.
6. Removed all animation, fully instant/synchronized switch — "animation harsh now :(" — confirmed the user wants a genuine animated transition, not a hard cut; the instant switch itself is not what "harsh" was describing in step 2 either, it turns out — "harsh" describes an abrupt, jarring change in general, whether caused by a mismatched partial animation or by no animation at all.
7. **Current approach**: stop animating any color entirely. `ThemeProvider` wraps the app's real content in a single `Animated.View` and dims its opacity from 1 → 0.4 (native-driven, `useNativeDriver: true`, 120ms, `Easing.out(Easing.quad)`), swaps `mode` in that animation's completion callback (content is mostly hidden at that point), then fades back to 1 over 180ms (`Easing.in(Easing.quad)`). This is a different technique in kind from every prior attempt: no per-color interpolation (so no JS-bridge stutter risk — opacity is nativizable), no partial split (the whole tree dims as one unit, so nothing can be out of sync with anything else), and no synthetic overlay color to get wrong (it's the actual UI, just briefly translucent, not a rectangle placed on top of it).
- Verified with `npx tsc --noEmit` from `mobile/`. **Not verified on a device** — this is the seventh distinct approach on this one feature this session, all reasoned from the user's text descriptions with no visual confirmation at any point. Strongly recommend the user check this on-device before further iteration; continued blind changes have low expected value at this point.
- Committed `mobile/lib/theme.ts` alone.
