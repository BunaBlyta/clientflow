# Mobile: deferred theme mode snap to fix "harsh" toggle feel

- User reported the theme toggle (light/dark), fixed earlier this session to crossfade real colors instead of an overlay flash, now felt "a bit harsh" compared to before.
- Checked git history for `lib/theme.ts` and `account.tsx` — no other agent touched either file since the earlier crossfade fix, so this wasn't a regression from concurrent work; it's a real gap in that fix.
- Root cause: only a small set of elements are wired up to `useAnimatedThemeColor` (the shared `AtmosphereBackground`, and the Account screen's heading/profile card/preference card/settings rows) — the rest of the app (icons, buttons, hairline borders, language options, every other tab) reads `color` from `mode` directly via `useTheme()`, which changes instantly. `ThemeProvider`'s `setMode` called `setCurrentMode(nextMode)` — the thing that flips `mode` — immediately when the toggle was pressed, before the 260ms crossfade animation even started. So every non-animated element on screen snapped to the new theme at t=0, while the handful of animated elements were still visibly mid-fade from the old color for the next 260ms — a jarring simultaneous mix of "already switched" and "still transitioning" for the whole duration.
- Fix: moved `setCurrentMode(nextMode)` into the `Animated.timing(...).start(({ finished }) => ...)` completion callback instead of calling it synchronously before the animation starts. The static elements now snap once, timed to land right as the animated elements finish arriving at the same destination color, rather than snapping at the start and clashing with the fade for its entire duration.
- Verified with `npx tsc --noEmit` from `mobile/`. Not verified on a device this session.
- Committed `mobile/lib/theme.ts` alone.
