## 1. The thing that nearly went wrong, and the rules that came from it

On Monday 10 August, roughly **7,800 lines of finished work sat uncommitted** across
four separate git checkouts — a complete Expo mobile app, most of the web dashboard,
and the Prisma schema. Nothing was pushed. Nothing had a remote. One bad `git
checkout` would have destroyed two days of work.

The cause was two configuration mistakes, not bad code:

1. **Claude Desktop was connected to `tetbit-app`**, a docs-only folder, while all
   the actual code lived in the sibling `clientflow`. Every session started blind
   and re-derived the state badly.
2. **Nobody committed.** Uncommitted work is invisible to every other checkout, so
   each agent thought less existed than actually did, which made them create *more*
   checkouts, which made it worse.

Everything was recovered and merged into `main` on Monday evening. The rules that
exist because of this are not style preferences — they are scar tissue:

- **Commit at the end of every task, and push.** If a task is finished and not
  committed, it is not finished.
- **Connect Cowork/Claude Desktop to `/Users/buna/Documents/tetbit`** (the parent),
  never a single subfolder.
- **One checkout, `clientflow/`, everyone on `main`.** No worktrees.

### Why worktrees were removed (do not reintroduce them)

Worktrees were tried and caused two distinct failures:

- Each worktree carries its own `node_modules`, which silently drifts out of sync
  with `package.json`. This is what broke the mobile app: a merge brought in a new
  `mobile/package.json`, `node_modules` stayed stale, and `expo-router` "vanished".
- 441 MB of an orphaned worktree stayed on disk after `git worktree remove`
  deregistered it. Because `.claude/worktrees/` is gitignored, nothing surfaced it
  — and Vitest later picked up 151 test files from inside it.

`SETUP_GUIDE.md` still contains the original worktree instructions. It has a
warning banner on it. **It is historical. Do not follow it.**

## 2. How the agents are organised, and why this split

Three Codex agents, **split by directory, not by feature**:

| Agent | Owns | State file |
|---|---|---|
| A — API & database | `app/api/**`, `prisma/`, `docs/ARCHITECTURE.md` | `status/CURRENT-api.md` |
| B — Web UI | `app/(marketing)/`, `app/(dashboard)/`, `app/(auth)/`, `middleware.ts`, `components/`, `lib/` | `status/CURRENT-web.md` |
| C — Mobile | `mobile/**` only | `status/CURRENT-mobile.md` |

A **feature split** (auth vertical / Stripe vertical / wiring vertical) was tried on
11 August and reverted within the hour. The reason is worth remembering: feature
verticals all needed `app/api/`, `lib/` and `mobile/`, so three agents would have
collided on the same files *and* blocked each other on dependencies. Directory
lanes cannot overlap by construction, and ran a full day with zero real collisions.

**Every state file has exactly one writer.** `status/CURRENT-*.md` per lane, and
`status/log/` where each entry is a brand-new file, never edited. This is the same
trick changesets and towncrier use for CHANGELOG files: collisions become
structurally impossible rather than merely unlikely. A file-locking scheme was
considered and rejected — it would depend on agents following a convention, and
conventions are exactly what failed on Monday.

### Buna runs migrations and installs, never the agents

`prisma migrate`, `npm install` and `npx expo install` are **Buna's alone**. Agents
print the command and stop.

This is the only guard here that was deliberately made environmental rather than
conventional, because concurrent migrations against a live Neon database and
concurrent installs corrupting a lockfile are the only two failures in this setup
that are **silent and painful**. Everything else fails loudly and is recoverable
from git.

Note the unintended consequence: told "never install", Agent A **designed around
the rule** rather than asking — it implemented Stripe and Resend over raw `fetch`
instead of pausing for two minutes. The result was good, but be aware that a hard
"never do X" can push an agent into inventing around X instead of surfacing it.

## 3. Every serious bug this week was found by running the app

Not one was caught by typecheck, lint or the build. All six were green throughout.
Two of them were found on the afternoon of 11 August by an agent that had shipped
code its own tests passed on, and could not have been found any other way.

1. **No root route in the mobile app.** Both route groups are `(auth)` and `(app)`
   — parentheses hide them from the URL, so nothing matched `/`. Invisible on a
   phone (the router just shows the first screen); an "Unmatched Route" error in a
   browser and on any deep link. Fixed with `mobile/app/index.tsx`.
2. **Five Zustand selectors causing infinite re-renders.** Selectors that ended in
   `.filter()` or `[...spread].sort()` built a new array on every call; Zustand
   compares by reference, so it looked like the state changed forever. Fixed with
   `useShallow`. **The React error pointed at `_layout.tsx`'s `<Tabs>`, which was
   innocent** — React blames the nearest navigator, not the looping component.
3. **Every tab bar in the web app rendered as a broken vertical stack.** `globals.css`
   defined `data-horizontal`/`data-vertical` variants matching a bare boolean
   attribute, but Base UI only ever emits `data-orientation="horizontal"|"vertical"`.
   The variants silently never matched. Broken for days; nobody had looked closely
   in a browser.
4. **An auth bypass.** `sessionSecret()` fell back to a hardcoded string committed
   to the repo, with no production guard. Since the token payload is just
   `{sub, exp}`, anyone reading the repo could have forged a session for any user,
   including staff. Now throws in production if `SESSION_SECRET` is missing.
5. **Mobile could not log in at all under `expo start --web`.** No CORS handling
   existed anywhere in `app/api/`. Expo's web build serves from port 8081 and calls
   the API on 3000, so the browser sent a preflight `OPTIONS`, got a 405, and
   blocked every request. **Native builds have no CORS**, so this is invisible on a
   device and invisible to every test — it only exists in browser mode. Fixed in
   `middleware.ts`, gated to `NODE_ENV === "development"` and localhost origins.
   Adding `/api/:path*` to the middleware matcher meant API routes had to return
   early, or an unauthenticated API call would have been redirected to `/login` and
   every caller would have parsed HTML as JSON — including the Stripe webhook.
6. **Stripe's redirect landed on a 404.** `app/api/stripe/checkout/route.ts` has
   always pointed `success_url` and `cancel_url` at `/payment/success` and
   `/payment/cancelled`. **Neither page existed.** The payment itself succeeded —
   the webhook is server-to-server and does not care where the browser went — so
   this was invisible in every log and in the database. Only paying with a real
   card surfaced it. Both pages now exist, unauthenticated (the payer arrives from
   Stripe, often with no web session).

**The lesson, stated plainly:** `npm run verify` catches regressions. It does not
catch "this renders wrong", "this is insecure", or "this whole path 404s". Click
through the app in a browser after every batch of work.

Bugs 5 and 6 sharpen the point: both were on the single most important path in the
project, both were shipped by agents whose typecheck, lint and tests all passed,
and both took under five minutes to find by actually paying an invoice.

## 4. Decisions that look odd but are deliberate

**Stripe and Resend are called over raw `fetch`, not their npm SDKs.** Neither
package is installed. Webhook signature verification is hand-rolled in
`app/api/_lib/stripe.ts` using `node:crypto`.

This was reviewed carefully and it is correct — including the part people usually
miss: it signs over `${timestamp}.${payload}` (Stripe's actual scheme, not just the
body), handles multiple `v1=` signatures, uses `timingSafeEqual`, and **enforces a
300-second timestamp tolerance to prevent replay attacks**. Without that window,
anyone who captured one valid webhook could replay it forever.

If a reviewer asks why not the official SDK: verifying against Stripe's documented
scheme directly, with tests, is a defensible answer. Do not swap to the SDK
casually — it would mean rewriting working, tested code.

**`transitionInvoiceStatus` returns true for a same-to-same transition** (`PAID` →
`PAID`). This is not sloppiness — it is what makes duplicate Stripe webhook
deliveries idempotent. Do not "tighten" it.

**`Project.packageId` is nullable in Prisma and in both frontend types.** Prisma is
right (AGENTS.md §4 — custom projects have no package). *An earlier version of this
document said the mobile type still needed fixing. It did not — it was already
nullable, and two agents wasted a summary line each re-reporting that. Fixed here
on 11 Aug.*

**The same class of bug did bite once, though.** `InvoiceKind` had to gain `CUSTOM`
in both frontends when `/api/invoices` shipped. Web's label map is typed
`Record<InvoiceKind, string>`, so typecheck forced the union to be widened.
**Mobile's is `Record<string, string>`**, so nothing failed, the label was added,
and the union was silently left with three values while the API returned four. If
you loosen a map's key type, you give up the compiler's help exactly where you need
it most.

**Two unused imports in `dashboard/projects/page.tsx`** (`PROJECT_STATUS_LABEL`,
`PROJECT_STATUS_TONE`) were left deliberately as a breadcrumb — they look like the
start of unfinished status work.

## 5. Environment gotchas that cost real time

- **Node 22 is required for anything Expo** (`nvm use 22`). SDK 57 needs 22.13+.
  Prisma also warns on Node 20. Consider `nvm alias default 22`.
- **Expo Go from the App Store cannot run SDK 57.** SDK 57 shipped 30 June 2026 and
  the store build lags. Use `npx eas-cli go` for a physical device, or
  `npx expo start --web`. This is not a project problem.
- **iOS Simulator needs full Xcode (~15 GB).** Not installed. Not required.
- **The iOS Camera app will not open the Expo QR code** — it does not handle the
  `exp://` scheme. Use "Enter URL manually" inside Expo Go.
- **Denying Expo Go's Local Network permission** reports itself as "internet
  connection appears offline". Fix in Settings → Expo Go → Local Network, then
  force-quit the app.
- **Codex sandboxes report a Turbopack failure** ("Operation not permitted" binding
  a port). This is their sandbox, not the project. `next build` works fine on
  Buna's machine. Only trust `npm run verify` run by Buna, with all agents idle.
- **`.env` is read only at dev-server startup.** After changing it, restart.
- **`stripe listen` issues a NEW `whsec_` each run.** If webhooks suddenly start
  returning 400, that is why.

## 6. Stripe: what is actually proven

Proven end to end on 11 August, verified in the database, not just in logs:

- Tunnel delivery, signature verification, and `inv-5` moving `SENT` → `PAID` with
  a `paidAt` timestamp written by the webhook.

**A caution that cost confusion once:** a bare `stripe trigger payment_intent.succeeded`
returns `[200]` but does *nothing*, because the synthetic event carries no
`metadata.invoiceId` and the handler correctly ignores it. Returning 200 to events
you ignore is required, or Stripe retries forever. To actually exercise the logic:

```
stripe trigger payment_intent.succeeded --add payment_intent:metadata.invoiceId=inv-5
```

**`[200]` in the listener proves delivery. Only the database proves the business
logic ran.**

`npx prisma db seed` is rerunnable and resets invoice statuses — use it to get a
clean slate before demoing.
